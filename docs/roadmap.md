## Conventions

- Each schema change is a new `src/data/migrations/000N_*.sql`, registered in
  `MIGRATIONS` (`src/data/migrate.ts`).
- New tables also go into: `EntityMap` (`src/domain/types.ts`), `TABLES` and `emptyState`
  (`src/domain/changes.ts`), `TABLE_SPECS` (`src/data/mappers.ts`), the export format and
  schema (`src/domain/export/`), and `devSeed`.
- Every write is a `ChangeSet` passed through `commit()`, so undo keeps working. Rows
  generated by the app itself (such as routine occurrences) use `{ noHistory: true }`.
- Each user-visible change adds a CHANGELOG "Unreleased" entry.
- Before committing, check:
  - `npm run lint && npm test && npm run test:tz`
  - in `src-tauri`: `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`
  - `npm run e2e:build && npm run e2e` (Linux, needs tauri-driver and WebKitWebDriver)

### Notes for the next session

- This repo was being edited by two Claude sessions in one checkout, and a `website`
  branch exists (a GitHub Pages site). Work on your own branch or worktree.
- Rebuilding `goals` inside a migration fires its `ON DELETE CASCADE`s. Use triggers or
  `ALTER TABLE … ADD COLUMN` instead (see `0002_integrity.sql`).
- The e2e suite can be flaky locally: WebKitWebDriver sometimes reports "page crash or
  hang" in the middle of a drag. CI retries each spec file once.
- The auto-updater and code signing need keys and accounts from the owner. Don't
  implement them without asking.
- ICS import has no timezone database: a UTC (`Z`) timestamp is converted to the host
  machine's local wall clock (correct); a floating or `TZID` timestamp is taken at face
  value, assuming it already matches the viewer's zone. Recurring events (`RRULE`) are
  not expanded — each `VEVENT` becomes at most one overlay event.

## M10: Planning power features (0.2.0)

1. **Copy week and week templates** (high value, low risk, builds on `copyPlanFrom` in `src/state/commands.ts:183`).
   - "Copy last week's plan" in the Week view header and in the empty-day prompt. It copies every day of the week in one `ChangeSet`.
   - **Templates:** a new `templates` table (`id, name`) and a `template_blocks` table (`template_id, weekday | null, start, end, title, goal_id`).
   - Actions: "Save this day/week as template" and "Apply template…" (from the context menu and the empty-day prompt).
   - Applying a template creates ordinary plan blocks, so they stay undoable. Templates never link to the blocks they created.
2. **Recurring plan blocks (routines).**
   - New `routines` table: `id, title, goal_id, start, end, weekdays bitmask, starts_on, ends_on`.
   - `blocks` gets a `routine_id` column and a `(routine_id, day)` unique index.
   - **Materialization:** when a week loads (`ensureWeek`), create plan blocks for any routine days from today onward that don't have one yet. Past days are never touched.
   - Deleting a materialized block records a `routine_exceptions(routine_id, day)` row so the block doesn't come back.
   - Editing the routine updates future unedited occurrences only.
   - Recommend shipping this after templates, because templates solve most of the need with less risk.
3. **Quick-add and keyboard creation.** Type `n` (or Enter on an empty focused slot) to open a one-line input like `9-10:30 Thesis #thesis`.
   - Parse it with a pure function in `src/domain/blocks/quickAdd.ts`. Reuse `parseTimeInput` and match `#` tags to goals by name.
   - This also closes the a11y gap that you can't create a block without a mouse.
4. **Command palette (Ctrl+K) and `?` shortcut sheet.** Both are already designed in `ux-interaction.md:34`.
   - Commands: go to date, apply template, confirm rest of day, switch goal, export.
   - Build it on the existing shadcn `dialog` (add `cmdk`).
5. **Highlight a goal.** Clicking a goal in `BudgetPanel` dims every other goal's blocks (add a UI state field in `src/state/ui.ts`).
6. **Drag to reorder outcomes and goals.** `sort_order` already exists in the schema; today goals can only move with the up/down buttons in `moveGoal`.
7. **Running block / timer.** "Start now" creates an actual block from now to now+snap. The clock tick in `src/main.tsx` extends it until you stop it. Show the running block in the window title.
8. **Blocks that cross midnight.** These were deliberately cut. Recommendation: keep them cut, and instead offer "split at midnight" when a drag goes past 24:00, creating two linked blocks. That way the wall-clock model stays as it is.

## M11: Desktop integration (0.3.0)

1. **Window state.** Add `tauri-plugin-window-state` to remember the window's size, position and maximized state. Trivial and visible.
2. **Notifications** (`tauri-plugin-notification`), each with a setting:
   - "Next block in 5 min: Thesis";
   - an evening "Today has 3 unconfirmed blocks" nudge, with a Confirm action that opens Day view;
   - "Weekly review is ready" on the last day of the week.

   Schedule them in the webview from the existing clock tick, with no background daemon. The app only has to be running, which suits a local-first app.
3. **Tray icon** (Tauri `tray-icon` feature) with: Today's next block, Start timer, Confirm rest of day, Show/Hide, Quit. Add a "close to tray" setting. Optional autostart (`tauri-plugin-autostart`).
4. **ICS import (read-only overlay) and ICS export.**
   - Import: a `.ics` file or URL becomes events shown as read-only blocks in a thin side track, with "Copy to plan".
   - Export: the plan and actual for a date range.
   - A pure parser goes in `src/domain/ics/` (consider the `ical.js` npm package). Network fetch for a URL needs an http capability, so start with file import only.
5. **Auto-update** (`tauri-plugin-updater`): generate signing keys, publish `latest.json` in `release.yml`, add a "Check for updates" setting.
   - This depends on your release setup. **Watch out for the daily-publish timer:** `origin` lags local `main` until about 2026-10-25, so don't ship the updater until releases are real.
6. **Signing/notarization** (macOS Developer ID, Windows Authenticode) and Flatpak. These cost money or accounts, so they're your call.

## M12: Insights and analytics (0.4.0)

1. **Trends view (`i` key).**
   - Per goal, over the last 4/12/26 weeks: a target line against planned and actual bars, and a streak of met weeks.
   - Data: add `repo.loadRange(fromWeek, toWeek)` (one indexed query on `blocks_day_layer`) and reuse `computeStats` from `src/domain/stats/stats.ts` week by week. Keep that loop pure and memoized.
   - Charts: plain SVG components like the existing `BulletBar`, so no chart library is needed.
2. **Plan accuracy stats.**
   - Measures: confirmed-as-planned %, skipped %, unplanned %, average start drift (actual start minus plan start for linked actuals).
   - Show them on the Review page and in Trends.
   - The calculation goes in `src/domain/stats/accuracy.ts`, using the existing `linksByPlan` and `planStates` from `reconcile.ts`.
3. **Delta badges on actual blocks** (`+15m late`, `goal changed`), as designed in the UX doc and never built.
4. **Review additions:** a "Biggest gaps" list (largest unplanned or unconfirmed stretches) and "Reschedule skipped → next week" (copies skipped plan blocks into a chosen day).
5. **CSV export** (blocks for a date range, plus weekly goal stats) next to the JSON export in `SettingsView`. A pure formatter goes in `src/domain/export/csv.ts`.
6. **Heatmap.** A year view with one cell per day, coloured by actual hours (or by a chosen goal's hours).

  - an e2e check that closing right after an edit keeps the edit after restart.
